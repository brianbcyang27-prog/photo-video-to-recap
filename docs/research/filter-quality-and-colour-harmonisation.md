## 1. The short version

Five things, in order of expected perceptual gain per unit of work:

1. **The pipeline is applying the BT.601 luma matrix to every still and then
   shipping the result untagged.** Every player reads that as BT.709. Measured
   across **40 library photos**: per-photo median ΔE76 **18.98 → 2.51 (7.6×)**,
   worst photo 105.69 → 4.01, and **0 of 40 photos got worse**. On a single
   maximally-saturated photo it is ΔE76 19.94 → 2.91. This is the single
   largest quality defect found, and the fix is one filter plus three tags.
   **[verified]**
2. **ffmpeg's `psnr` / `ssim` / `libvmaf` filters pair frames by timestamp, not
   by order.** On mismatched timebases they silently compare the wrong frames
   and will report a near-lossless encode as VMAF 67.03 instead of 99.94. Any
   verifier you write *must* normalise both legs. **[verified]**
3. **The most heavily weighted selection criterion in `select.py`
   (`w_sharpness = 0.30`, a flat `variance-of-Laplacian` floor of 60) is the one
   sharpness metric with the largest documented failure modes** — depth-of-field
   background, texture density, watermarks and noise all move it independently
   of focus. **[verified]** for the mechanism, **[reported]** for the literature.
4. **The `format=yuv420p,setrange=limited` at the end of every still chain is a
   bit-exact no-op.** SHA-256 of the output is identical with and without it.
   It reads as a correctness guarantee and guarantees nothing. **[verified]**
5. **`accurate_rnd` and `full_chroma_int` are also bit-exact no-ops** on ffmpeg
   ≥ 5.x, so ASWF's "use `lanczos+accurate_rnd`" guidance buys you exactly
   nothing measurable here. The scaler algorithm is the only thing that
   matters. **[verified]**

Everything else in this report is worth doing, but none of it is worth as much
as items 1–3.

## 2. Finding 1 — the colour matrix. The biggest defect in the pipeline.

### 2.1 What the code does

`pipeline/render.py::render_still()` builds:

```
-loop 1 -framerate 30 -i shot.png  -vf  <zoompan…>,format=yuv420p,setrange=limited
```

`shot.png` is `RGB24` from Pillow. The first ffmpeg filter that needs YUV is
`format=yuv420p`, and ffmpeg auto-inserts a `scale` to perform the RGB→YUV
conversion. **No `out_color_matrix` is given, so ffmpeg uses its default.**

### 2.2 What ffmpeg's default actually is

Measured, by running the pipeline's exact chain and comparing the output's
SHA-256 against chains where the matrix is named explicitly **[verified]**:

| Chain | SHA-256 (first 16) of output |
|---|---|
| `format=yuv420p,setrange=limited` (pipeline) | `22e428884df348f3` |
| `format=yuv420p` (no `setrange`) | `22e428884df348f3` — **identical** |
| `scale=…:out_color_matrix=bt709,…` | `d4322d994ac6969e` |

And decoding each as a player would:

```
pipeline-default vs explicit bt601 : ΔE76 mean 0.00   (bit-identical)
pipeline-default vs explicit bt709 : ΔE76 mean 11.56
```

**ffmpeg's default RGB→YUV conversion is bit-for-bit BT.601.** The pipeline is
rendering every still with BT.601 luma coefficients. For 1920×1080 output the
correct matrix is BT.709.

### 2.3 And the result is shipped untagged

`ffprobe` on the pipeline's output segment:

```
color_range=unknown   color_space=unknown   color_primaries=unknown   color_transfer=unknown
```

Every player resolves "unknown" as **BT.709** for HD. YouTube says so
explicitly in its official upload spec: *"When the upload color space has
unknown or unspecified color matrix and primaries → Assumes BT.709 color
matrix and primaries."* **[verified]**

So the file is **written** as BT.601 and **read** as BT.709.

### 2.4 The measured cost

Round trip: source JPEG → RGB PNG reference → pipeline chain → H.264 → decode
as BT.709 → CIE76 against the RGB reference, on `IMG_day1_0004.jpg`
(RGB mean 154/54/140, i.e. a heavily saturated magenta — worst case).

| Variant | ΔE76 mean | ΔE76 p50 | ΔE76 p95 | resulting LAB mean |
|---|---|---|---|---|
| Pipeline as-is (601 coeff, untagged, read as 709) | 123.69 | **19.94** | 603.30 | `[90.4, 14.00, −9.01]` |
| **Fixed** (explicit bt709 matrix + tags) | 10.11 | **2.91** | 10.59 | `[88.69, 13.60, −11.28]` |
| Control: pipeline read as 601 (what ffmpeg's own default assumes) | 7.95 | 3.39 | 9.92 | `[88.63, 10.47, −11.19]` |
| Control: fixed file read as 601 (the mistake in reverse) | 130.77 | 28.17 | — | — |

**[verified]**

The `p95` of 603 in row 1 is a clipping artefact at the synthetic image's
saturated magenta extremes; the honest number to quote is the **median, ≈20
ΔE76**, against a just-noticeable-difference threshold of roughly 2.3 ΔE **[reported]**.
Row 4 is the control that proves the effect is symmetric and real: mis-tagging a
*correct* file as BT.601 costs the same magnitude.

The rest of the round-trip error (ΔE76 ≈ 7.95, chroma ≈ 9.33) is 8-bit 4:2:0
chroma subsampling, which is unavoidable at this bit depth. **The matrix is a
larger error than the subsampling** — and the matrix is free to fix.

#### 2.4.1 The same measurement across the whole library

One saturated synthetic image is a worst case, not a typical case. Repeating
the identical round trip on the **first 40 photos of the library**, reporting
the per-photo median ΔE76 (a robust central estimate, immune to the clipping
artefacts that dominate the `mean` and `p95` columns):

| | per-photo median, **median** | mean | min | max | mean of per-photo p95 |
|---|---|---|---|---|---|
| Pipeline as shipped | **18.98** | 25.69 | 0.00 | 105.69 | 396.80 |
| **Fixed** (`out_color_matrix=bt709` + tags) | **2.51** | 2.37 | 0.00 | 4.01 | 8.35 |
| Improvement | **7.6×** | 10.8× | — | **26×** | 47× |

**[verified]** — ffmpeg 9.0.1, macOS arm64, 40 photos, lossless round trip
(`-qp 0`), decode forced through `scale=in_color_matrix=bt709` to simulate a
player resolving the untagged stream. Script: `matrix_all.py`, see §12.

Three things this table settles that the single-image result could not:

1. **The defect is not a worst-case artefact.** 18.98 ΔE76 is the *typical*
   error in this library, and the worst photo is 105.69. Even a mildly
   saturated mid-tone is off by ~19 ΔE76.
2. **The fix never makes a photo worse.** Per-photo deltas: **0 of 40 photos
   got worse**, 38 improved, 2 were unchanged (both are effectively neutral
   images, where the two matrices agree because there is no chroma to
   misplace). Every single delta in the per-photo table is ≤ 0. A fix with no
   regressions across a mixed corpus is safe to ship blind.
3. **The fix lands on the subsampling floor.** The residual median of 2.51 is
   not "residual colour error" — it is 8-bit 4:2:0 chroma subsampling, which is
   inherent to `yuv420p`. The corroborating number is in §2.4 row 3: the *same*
   image decoded along ffmpeg's own default assumption (read as BT.601, i.e. no
   matrix error at all) still costs 3.39 median ΔE76, and the BT.709 fix scores
   **2.91** — slightly *better*. There is no colour headroom left above
   `yuv420p`; getting the matrix right is what buys you the right to stop
   worrying about colour.

The caveat from §0 applies with full force: this corpus has an independent
random hue per photo, so the *distribution* of 18.98 is inflated relative to
real travel footage. The *existence, sign, and monotonicity* of the effect are
properties of ffmpeg's default and do not depend on the corpus. The maintainer
should still re-run the script on the real library before quoting a number in
a changelog — expect a smaller median, not a different conclusion.

### 2.5 The fix

Cheapest correct form, for stills and video alike:

```python
"-vf", f"{chain},format=yuv420p",
"-color_primaries", "bt709", "-color_trc", "bt709", "-colorspace", "bt709",
"-color_range", "tv",
```

That tags the *output*, which is correct for every consumer. If you want the
conversion itself to be right rather than merely the tag:

```
scale=in_range=full:out_range=limited:out_color_matrix=bt709
```

Note the subtlety: **tagging BT.709 without also doing the conversion is
strictly worse** — it converts a BT.601-encoded file into a file that lies
about itself. You need the `scale` *and* the tags. **[verified]**

The same tags should go on `render_video` and `render_live`. Those read yuv420p
source directly so no conversion happens and the tags cost nothing — but they
also currently emit `unknown`, which means a phone clip shot in BT.601 (common
for SD-ish phone profiles) would be misread.

**Drop `setrange=limited`.** It is a no-op here (row 2 of §2.2) and it implies a
guarantee it does not provide. Use `-color_range tv` on the output instead,
which is a tag, not a transform.

## 3. Finding 2 — ffmpeg's quality filters desync silently

This one matters because your entire verifier rests on measuring the rendered
file.

### 3.1 Symptom

Comparing the rendered recap against a lossless reference of the same source:

```
psnr    : 26.05 dB average
libvmaf : 67.03
ssim    : 0.8471
per-frame VMAF min: 0.0   (37 of 112 frames below 50)
```

For a near-lossless re-encode. That combination — a *good* average, a *zero*
minimum, and a scattering of catastrophically bad frames — is the signature of
a **frame-pairing** bug, not a quality problem.

### 3.2 Ground truth

Decoding both legs frame-by-frame in display order and comparing index-to-index:

```
mean PSNR 45.25 dB   median 45.19   min 43.75
```

Perfectly uniform, min within 1.5 dB of the mean. **[verified]**

### 3.3 Root cause

Matroska PTS are millisecond-quantised: `0, 42, 83, 125, 167, 208, 250, 292`.
MP4 tracks a 1/24 s grid exactly: `0, 512, 1024, 1536 …` in 90 kHz ticks.
ffmpeg's `framesync` (which `psnr`, `ssim`, `libvmaf`, `xfade`, `overlay` all
use) **matches frames by timestamp, not by arrival order.** With two different
timebases it pairs frame *n* of one leg with frame *n±1* of the other, and
sometimes pairs the same frame twice.

Ruled out by experiment **[verified]**:

| Hypothesis | Test | Result |
|---|---|---|
| Threading race | `libvmaf n_threads=1…8` | identical scores at every thread count |
| Colour range | `in_range=tv` vs `full` | identical |
| Frame shift | manual `select=eq(n,2)` extraction | 45.79 dB — *correct* alignment |
| Metadata | same file, `-vf null` vs filters | identical |

The last one is the clincher: manual per-frame extraction in display order
gives 45.79 dB. The content was always correct; the *comparison* was wrong.

### 3.4 The fix, and what it is worth

```python
NORM = "settb=AVTB,setpts=N/(24*TB),format=yuv420p"
cmd = ["ffmpeg", "-i", "reference.mp4", "-i", "rendered.mp4",
       "-lavfi", f"[0:v]{NORM}[a];[1:v]{NORM}[b];[a][b]libvmaf=n_threads=8",
       "-f", "null", "-"]
```

| | unfixed | fixed |
|---|---|---|
| VMAF | 67.03 | **99.94** |
| SSIM | 0.8471 | **0.9931** |
| PSNR | 26.05 dB | **48.36 dB** |

**[verified]**

The alternative — and arguably the better engineering choice — is to make both
legs share a container and timebase by construction. If the verifier encodes its
reference the same way it encodes the deliverable (same `-video_track_timescale`,
same muxer), framesync can never disagree. Belt and braces: do both.

**Design rule for the verifier:** never let a measurement pass or fail on a
frame index it did not compute itself. Either normalise both legs, or compare
via `select=eq(n\,K)` on both sides, or compare decoded rawvideo buffers in
numpy. The third is what `tools/verify_output.py` already does for orientation
and detail checks — apply the same discipline to encoder fidelity.

## 4. MEASURED NUMBERS

Everything in this section was produced in this session on the rig described in
§0. Commands are reproducible from `/private/var/folders/…/T/opencode/qexp/`.

### 4.1 `accurate_rnd` / `full_chroma_int` are no-ops on ffmpeg 9.0.1

**[verified]** — SHA-256 of raw output, all four identical:

```
scale=1920:-2:flags=lanczos                              → 0f3c…  (identical)
scale=1920:-2:flags=lanczos+accurate_rnd                 → 0f3c…  (identical)
scale=1920:-2:flags=lanczos+full_chroma_int              → 0f3c…  (identical)
scale=1920:-2:flags=lanczos+accurate_rnd+full_chroma_int → 0f3c…  (identical)
```

Only the scaler algorithm changes bytes: `lanczos` ≠ `bicubic` ≠ `spline`.

This confirms, on current ffmpeg, the ASWF Encoding Guidelines' own hedge:
*"we have yet to find a case where this currently makes a difference."* **[reported]**
The guideline's practical recommendations still hold — `lanczos` for
RGB→Y′CbCr downsampling of live action, `spline` for 4:4:4→RGB, and the
acknowledgement that *"it's frankly hard to say between zscale and swscale
which is better"* **[reported]**. But do not spend a cycle on the flags.

### 4.2 Ken Burns supersampling

`render.py` uses `ZOOM_SS_CAP = 2`, justified in-code by a measurement on a
real 4032×3024 photo: edge energy **5.402 → 5.688 → 5.700** at 1×/2×/4×
("2× takes essentially all of the available gain").

Independently re-measured here with a different methodology — 1920×1080
`testsrc2`, z = 1.0→1.5 over 100 frames, reference = an 8× supersampled render,
and motion measured as the σ of the *second difference* of the tracked centroid
(motion jitter, dimensionless as a fraction of per-step travel):

| Supersample | PSNR vs 8× ref | SSIM vs 8× ref | var(Laplacian) | % of Laplacian deficit recovered | jitter | jitter/step |
|---|---|---|---|---|---|---|
| 1× (none) | 30.86 dB | 0.9702 | 309.39 | 0 % | 457 123 | 14.04 % |
| 2× | 37.45 dB | 0.9881 | 356.22 | **70 %** | 395 485 | 12.30 % |
| 4× | 39.61 dB | 0.9926 | 372.36 | **94 %** | 301 438 | 9.32 % |
| 8× (reference) | — | 1.0000 | 376.58 | 100 % | 55 611 | 1.72 % |

**[verified]**

**These two measurements disagree, and the disagreement is the interesting
part.** On synthetic `testsrc2` (hard edges, deep high-frequency content),
2× recovers 70 % and 4× recovers 94 %. On a real camera JPEG, 4× added only
0.2 % over 2×. That is not a contradiction — a 4032 px photo has already had
everything above its optical/diffraction limit destroyed by the lens, sensor and
JPEG, so there is no fourth octave of detail for 4× to recover. `testsrc2` has
one.

**Conclusion:** `ZOOM_SS_CAP = 2` is the right choice, and the in-code
justification is sound. My jitter column is the genuinely new datum: **zoompan
quantises crop coordinates to integer source pixels, so pan jitter scales
roughly as 1/input-width** — a 12.3 % per-step jitter at 2× on this synthetic
source. On real photos at 2× the same fractional jitter exists but is far less
visible because the underlying detail is smoother. **Do not raise the cap.**

The one real improvement here is to reduce the jitter the pipeline already
pays: `vf_zoompan: fix shaking when zooming` (Trac #4298) rounds crop
coordinates to a chroma grid. Because supersampling multiplies the *output*
width but not the *source* width, `zoompan`'s integer rounding happens at the
source resolution in all cases. If jitter ever shows up in real output, the fix
is to increase the supersample (which this data says does help jitter, 12.3 % →
9.3 % at 4×), not to work around the filter.

want. **Sweep your own library before changing the default.**

**[verified]**

| ultrafast | **99.959** | 0.97898 | 43.75 | 25 654 | 2.61 |

**A negative result, and an important one: do not change `preset`.** `veryfast`

demonstration that a saturated metric can invert a ranking. This is exactly the
Netflix finding on PSNR/SSIM/VMAF correlation (§6.1), reproduced locally.

  matched SSIM, −30 % at matched PSNR.** On real grainy content the published

- **x265 `slow` beats x265 `faster`/`medium` by a wide margin at equal

  **[reported]**; the PSNR-matched framing hides that because PSNR itself
  flatters hardware codecs.

  universally decodable, and the pipeline already stream-copies segments into
  an MP4. Offer `libsvtav1` as an *optional* `--codec` for archival, with
  `--preset 6 --crf 30 --svtav1-params tune=0` per SVT-AV1's own documentation
  **[verified]** — SVT-AV1 documents `tune=0` as the subjective/VQ mode and
  recommends `crf=30` as a 1080p starting point **[verified]**.

### 4.7 Colour harmonisation — measured coherence reduction

40 library photos, scored as the median/p90/max pairwise CIE76 distance
between per-photo LAB centroids. Lower = more unified.

| Method | median ΔE | p90 ΔE | max ΔE | reduction | mean per-pixel drift (0–255) |
|---|---|---|---|---|---|
| **as shot, no harmonisation** | 75.5 | 156.2 | 277.5 | — | — |
| Reinhard LAB mean+σ, all three channels | 70.0 | — | — | +7.3 % | 78.1 |
| Reinhard LAB mean+σ, chroma only (L untouched) | 70.8 | — | — | +6.2 % | 77.8 |
| Reinhard reciprocal scaling, chroma only | 92.5 | — | — | **−22.4 %** | 80.3 |
| Shades-of-Grey p=6 → match LAB a\*,b\* | 72.1 | — | — | +4.6 % | 78.5 |
| **Grey-world (channel means → library mean)** | **45.9** | — | — | **+39.2 %** | 34.6 |

**[verified]** on this synthetic corpus.

Read this table carefully, because the obvious conclusion is wrong. The
methods that *preserve relative contrast* (Reinhard's σ matching, SoG) barely
move the metric — **because on a corpus with random independent hues, forcing
every image to identical σ destroys each image's own contrast, which is the
one thing a viewer should still perceive as different.** Grey-world wins here
only because it is the least destructive and this corpus has nothing but hue
variation to remove.

The mean per-pixel drift column is the real result: grey-world moves pixels by
**34.6** levels on average; every LAB-σ method moves them by ~78–80. **A
harmonisation pass that repaints the picture 78 levels out of 255 is not
harmonisation, it is a re-grade.** On synthetic gradients that survives; on a
real photo it will not.

The honest conclusion: **on this corpus the classical LAB methods cannot be
shown to be safe, and the only thing shown to be safe is the weakest possible
intervention.** See §7 for the design that follows from that.

## 6. Quality measurement and verification practice

### 6.1 Which metric to believe

From the 789-stream / 320 294-subjective-rating study *"Applying Objective
Quality Metrics to Video-Codec Comparisons"* **[reported]**:

| Metric | SROCC vs DMOS on Netflix content |
|---|---|
| PSNR | 0.6218 |
| SSIM | 0.5638 |
| MS-SSIM | 0.7136 |
| VIF | 0.7784 |
| **VMAF 0.6.1** | **0.9254** |

Netflix's own 2016 techblog is blunter: at a fixed 35 dB PSNR, DMOS ranges from
10 to 100 — **PSNR cannot distinguish a good encode from an awful one at equal
PSNR** **[reported]**. VMAF 93–95 is where Netflix considers a stream
"indistinguishable from original" **[reported]**, and arithmetic-mean pooling
performs best.

Two practical caveats for using VMAF here:

- **ffmpeg's `ssim` is not VMAF's SSIM** — VMAF's variant includes an empirical
  downsampling step, so the numbers are not comparable **[verified]**.
- **VMAF saturates.** §4.4 shows `ultrafast` *beating* `slow` on VMAF while
  losing 0.009 SSIM. Use VMAF for a floor ("is anything badly broken?") and
  SSIM/PSNR for ranking. **For codec comparison use VMAF NEG** — VMAF can be
  gamed by preprocessing **[verified]**.

### 6.2 Sharpness metrics: the failure modes, with sources

`config.py` sets `min_sharpness = 60.0` as a hard reject and `w_sharpness = 0.30`
as the largest single weight in the scoring function. Both are variance-of-
Laplacian. Here is what that metric is documented to get wrong:

| Failure mode | Evidence | Consequence here |
|---|---|---|
| **Depth-of-field background.** Shots with large, naturally out-of-focus backgrounds (aperture) are classified as blurry. | Vysotska et al., COLINS 2024: *"when using the default implementation, the FFT and Variance of the Laplacian methods are not reliable for evaluating sharpness for images containing large and unstable quantities of naturally blurred background (due to the open aperture)"* — and the proposed fix is to **evaluate sharpness only inside detected subject/face boxes** **[reported]** | Your `quality.py` *already has* `face_count()`. It computes the face count and throws the boxes away. The fix is ~10 lines. |
| **Texture density.** High-frequency texture raises Laplacian variance even in blurry images. | *Is it blur or is it texture?* (SPIE JMI 2023): blur measures "can be influenced by texture information in an image… users need to practice caution in the way results are interpreted" **[reported]**; a community benchmark reports accuracy stuck at 0.73 regardless of threshold, degrading on foliage/landscape **[reported]** | A foliage-heavy landscape photo scores high; a smooth portrait of the same sharpness scores low. |
| **Watermarks and text overlays.** | arXiv 2304.03156: adding a text watermark raised **mean Laplacian-map 10.7 % and std 39.8 %**; Tenengrad **mean +9.5 %, std +30.2 %** **[reported]** | iPhone/Samsung burn-in is common in phone libraries. |
| **Sensor noise and ISO.** | Same arXiv: "Laplacian operator is highly sensitive to the noise in the input image when compared to Sobel" **[reported]** | High-ISO night shots score as "sharp" when they are noise-dominated. |
| **Plain images.** | Same arXiv: patch-wise methods "fail when none of the patches in the image contain features… in these cases the images are classified as blur" **[reported]** | A flat sky or a white wall hard-fails at threshold 60. |

**Concrete fix, in increasing order of cost:**

1. **Normalise sharpness by the image's own contrast budget.** `laplacian_var /
   (std(gray) ** 2)` or a normalised-Laplacian (Kraft 1994 **[reported]**)
   removes the exposure dependence. Cheap, big win.
2. **Restrict the measurement to face boxes when faces exist.** You already
   detect them. This is the single highest-value change and costs nothing.
3. **Use a percentile, not the variance.** `np.percentile(|lap|, 95)` is far
   less outlier-sensitive than `np.var(lap)`.
4. **Keep the absolute floor as a secondary gate, not the primary signal.**

### 6.3 What the verifier already does well

`tools/verify_output.py` is unusually good and should be read as the model:
it checks properties a good render *must have* rather than diffing against a
golden file. Specific strengths worth preserving **[verified]**:

- It reuses `pipeline.quality.load_image`, so formats the pipeline accepts
  (HEIC) are also readable there — using `PIL.Image.open` directly made the
  verifier crash on exactly the files the pipeline handled fine.
- Orientation is checked by comparing the on-screen band against *both*
  hypotheses (recorded orientation vs stored pixels), sampling the correct half
  of a two-up spread. It was written because 106 of 141 photos shipped sideways
  while every other check passed.
- Thresholds are calibrated against deliberately-broken controls (a blurred
  second half at 0.444 vs a correct one at 0.944; a linear-ramp build scoring
  ≤ 1.05 vs an eased build ≥ 1.42).
- Motion is judged by *distribution of per-step displacement*, not magnitude,
  because magnitude is content-dependent and a fixed allowance fails on a
  different library. And the interior-only sampling fix is documented: including
  `t=dur` measures the cut, not the motion.

### 6.4 What the verifier is missing

1. **Encoder fidelity.** There is no check that the rendered file actually
   matches what the filter graph was asked to produce. Add §3.4's normalised
   `libvmaf` + `ssim` + `psnr` against a `-qp 0` reference render of the same
   EDL. This is the single highest-value addition, and it would have caught §2.
2. **Colour.** No check that the output carries correct colour tags, and no
   measurement of cross-shot colour coherence. See §7.
3. **A negative control on the colour/matrix path specifically.** The verifier
   has negative controls elsewhere; a build with the BT.709 tag removed should
   fail a new colour check.
4. **Sharpness measured *on the output frames*.** It is used for selection but
   never asserted on the render. A shot that passes `min_sharpness` at analysis
   scale can still render soft if `zoompan` or the scaler loses detail.

## 7. Colour harmonisation — the deep dive

### 7.1 Why this is the biggest *perceptual* lever

A viewer tolerates a mediocre cut. A viewer does not tolerate the film changing
from warm to cold to green between adjacent shots — it reads as "cheap" or
"automatic", which is exactly the perception you are trying to avoid.

The project scores `w_color = 0.12` via `colourfulness()`, which measures *how
much* colour a shot has (Hasler & Suesstrunk). It has no term at all for
*whether shots agree with each other.* **[verified]** Adding a coherence term is
a different and larger lever than re-weighting the existing one.

### 7.2 The hard constraint: no metadata

Every photo in the library is `yuvj420p`, `color_space=bt470bg`, with transfer
and primaries `unknown`, and **EXIF fully stripped** — no white balance, no
colour temperature, no profile **[verified]**. Every video clip carries
`color_space=color_primaries=color_transfer=unknown` **[verified]**.

So there is nothing to read. **Everything must be inferred from pixels.** This
rules out the professional approach and also rules out a lot of clever ideas.

### 7.3 What the profession actually does, and why you cannot

DaVinci Resolve's Color Match requires an **in-frame** X-Rite ColorChecker /
Datacolor SpyderCheckr / DSC Labs SMPTE OneShot chart lit by the same source as
the scene, with parameters for Source Gamma, Target Gamma, Target Colour Space,
Target Colour Temperature (default 6500 K) and Target White Level **[verified]**.
Resolve's own documentation states the underlying reason: *"an algorithm is
unable to recognize the environmental factors behind scene colors"* **[verified]**.
Resolve also ships a chart-free "Shot Match to This Clip", and practitioners
report it "rarely matches" **[reported]**.

You have no chart, no EXIF, and no RAW. You are in the worst case Resolve is
designed around, and you have to solve it in numpy.

### 7.4 The literature, honestly summarised

| Method | Idea | Measured (published) | Fit here |
|---|---|---|---|
| **Reinhard et al. 2001**, "Color Transfer between Images", IEEE CG&A 21(5):34–41 | Match per-channel mean and σ in lαβ/LAB | — | The reference implementation. Reinhard's own paper says the method "does not always produce aesthetically pleasing results" **[verified]**. |
| `jrosebr1/color_transfer` | Reinhard, plus a `preserve_paper=False` variant using the **reciprocal** scaling factor | — | The de facto Python implementation. Verified source: with `preserve_paper=True` it scales by `σ_target/σ_source`; with `False` by `σ_source/σ_target` **[verified]**. |
| **Finlayson & Trezzi 2004**, "Shades of Gray and Colour Constancy" | Minkowski-norm family `M_n^p` | Mean angular error, group A / group B: p=1 → 9.78/8.27; p=4 → 5.59/7.93; **p=6 → 6.29/7.71**; p=∞ → 9.16/9.77 **[reported]** | p=6 is the standard pick, but note p=4 and p=6 are within noise of each other on the group-A figure. |
| Colorconstancy.com benchmark | Cross-method | Shades-of-Grey SFU Lab mean 6.4°, median 3.7°; ColorChecker (Shi) mean 4.9° **[reported]** | Reference numbers. |
| **Counter-evidence** | A 2025 spectrally-rendered study found White-Patch and Gamut-Mapping best for whole-scene *perceptual* matching, and that human colour constancy is better approximated by whole-scene stabilisers than by illuminant estimators **[reported]** | — | Meaningful: **you are matching scenes, not illuminants.** Do not build an illuminant estimator. |
| Pitie MKL / MVGD (Pitié & Kokaram 2007) | Monge–Kantorovich linear optimal transport | — | The principled alternative to mean/σ matching; no numpy implementation exists. |

**Important disambiguation:** the "video harmonization" literature (Tsai et al.
and successors) is about *compositing a foreground person into a background* —
a different problem. The relevant lineage for this pipeline is Reinhard et al.
colour transfer, not harmonization.

### 7.5 What §4.7 actually measured, and the design that follows

The measured result (§4.7) is that on a hue-randomised corpus:

- σ-matching methods (Reinhard both ways, Shades-of-Grey + match) reduce
  cross-shot colour distance by only **5–7 %**, and one variant makes it **22 %
  worse** — while repainting every pixel by ~78 levels.
- Grey-world — the weakest possible intervention — reduces it by **39 %** while
  moving pixels by 35 levels.

Three design conclusions, each of which I can defend:

**(a) Never match σ. Match μ only.** Per-channel σ matching is what turns a
harmonisation pass into a re-grade, and it is the part of Reinhard that the
author himself disowns. In a montage every shot is a *different scene*; forcing
them to identical contrast is a category error.

**(b) Interpolate toward the library median, don't snap to it.** Instead of
`lab += (target_mean − mean)`, do `lab += λ(target_mean − mean)` with
`λ ∈ [0.5, 0.7]`. That preserves some of the sense that the sunset shot *was*
warm, which is half the reason it was worth filming, while removing enough
spread that the film reads as one film. λ is a single tunable knob and it is the
one thing a human should be able to override.

**(c) Do it in a perceptually uniform space, per-shot, before any Ken Burns
or resize.** SoG p=6 in linear RGB for the illuminant-normalisation step, then a
LAB a\*/b\* mean offset, then nothing. Three steps, ~30 lines, one pass.

**(d) Never touch L\*.** Exposure differences are semantic: a night shot
should stay darker than a beach shot. Only a\* and b\* move.

**(e) Robust target.** Use the library **median** LAB a\*/b\* centroid, not the
mean — one wild magenta night shot otherwise drags the whole film. Better still:
use a per-chapter or per-cluster target so each day has its own coherent look.
That is a genuinely professional move (a grade, not a correction) and it is two
extra lines given that `pipeline/geo.py` already clusters by day and place.

**Guard rails, all measured or sourced:**

- Clip the per-channel gain to `[0.85, 1.18]`. Below/above that the image stops
  looking like itself. §4.7 shows unbounded methods drifting 78 levels.
- Compute the coherence score and *store it in the EDL*, next to the existing
  per-entry metrics, so the verifier can assert on it like everything else. A
  coherence regression should be as loud as a duration regression.
- On the verifier side, add a **median pairwise chroma-distance check across
  consecutive entries**, with a floor calibrated against a deliberately
  un-harmonised build — the same calibration discipline the existing checks use.

### 7.6 What this is worth, honestly

I cannot give you a perceptual-quality number for harmonisation, because no
validated metric for "does this look professionally graded" exists and I am not
going to invent one. What I can give you:

- **[verified]** the library is, as shot, wildly incoherent (median pairwise ΔE76
  75.5, p90 156, max 278 on the synthetic corpus).
- **[verified]** the cheapest safe intervention removes ~39 % of that spread at
  ~35 levels of pixel drift.
- **[reported]** the professional workflow that removes the rest requires a
  physical chart you do not have.

So: do the cheap thing, make it a knob, measure the coherence, and stop. A
grade you can dial is worth more than a grade you cannot.

**The auto-editor `--margin` idea is the one worth adopting outright.** Your
cuts land exactly on the beat (verifier asserts it, correctly). But a cut with
*zero* handle reads as a jump cut. Cutting **2–3 frames early and 2–3 frames
late** around each beat gives the edit a handle while keeping the beat-aligned
cut point. That is one change in `arrange.py` and it is worth more than any
codec change in this report after §2.

## 9. Design and typography

### 9.1 The title-card layer is doing real work — keep it in numpy

`render.py` renders title cards and end cards with **Pillow**, not ffmpeg.
That is the right call and should not change:

- No font dependency, no `libass`/`--enable-libfreetype` requirement, no
  HarfBuzz shaping, no `fontsdir` path that breaks on another Mac.
- `canvas.save(out_png, quality=94)` means the title is a *source* for the same
  `zoompan` chain as a photo, so it is supersampled and lanczos-reduced
  identically.
- Subpixel antialiasing is preserved because Pillow composites in RGB.

What *is* missing:

| Issue | Detail |
|---|---|
| **Font fallback is fragile** | `_FONT_CANDIDATES` tries four paths. `SFNS.ttf` is a system-protected file on modern macOS and `ImageFont.truetype` on it may fail or return the wrong face. Verify at import time and fail loudly rather than silently rendering with `load_default()`. |
| **No optical sizing / no tracking** | `Arial Bold` at one weight is fine but flat. Tracking titles out by ~1.5 % of the cap height is the single cheapest thing that makes text look designed rather than generated. Pillow draws character-by-character, so this is easy. |
| **No contrast guarantee** | The verifier checks title legibility by counting near-white pixels in a band. A white title over a bright sky passes that check and is unreadable. Measure contrast *locally*: sample the luma distribution behind the text box and assert a minimum contrast ratio, or draw a scrim. |
| **No safe-area awareness** | See §9.2. |
| **Line length and hierarchy are fixed** | `title` and `subtitle` are two lines. Long place names like "Buenos Aires" at the current size on a two-up spread will overflow or collide. |

### 9.2 Safe areas — and a warning about the numbers

The project renders **1920×1080 landscape by default**, with portrait sources
handled by `two_up` and blur-fill. So classic broadcast title-safe applies, not
the vertical-feed safe zones. But if you ever ship a 1080×1920 cut, this
matters enormously.

**The published safe-zone numbers on the web disagree by up to 2.8×** **[reported]**.
The only measurements I found that came from the platforms' own artefacts were
taken by reading the alpha channel of their downloadable overlay templates
**[reported]**:

| Platform | Top | Bottom | Left | Right | At 1080×1920 |
|---|---|---|---|---|---|
| TikTok (current In-Feed template) | 12.5 % | 34.4 % | 11.1 % | 11.1 % → **17.8 % below mid-frame** | 240 / 660 / 120 / 300 px |
| Meta (Reels / FB / IG) | 14 % | 35 % | 6 % | 6 % | 269 / 672 / 65 / 65 px |
| YouTube Shorts (Shorts-only) | 10 % | 25 % | 0 % | 10 % | 192 / 480 / 0 / 108 px |
| YouTube (all placements) | 15 % | 35 % | 4.4 % | 17.8 % | 288 / 672 / 48 / 192 px |

The universally-cited "780×1270 px" and "810×1186 px" numbers circulating on
creator-tool sites match no platform template, current or archived **[reported]**
— treat them as **[rumoured]**.

Note also the L-shape: on TikTok the right margin *widens* below the halfway
point, and on Meta the rightmost 21 % is unsafe to 40 % of frame height. A plain
rectangle overlay understates the corner.

Your existing design already does the hard part of this correctly: `two_up`
puts two photos in the central columns, which is exactly the recommendation

advice is consistent across every source: **never put critical text in the
bottom 25 %**, because that is where the platform's own caption and username
go. **[reported]**

### 9.3 Grain as a unifying texture

This is a technique, not a filter, and it is worth considering specifically for
mixed-source montage:

- Mixed phone footage has inconsistent **noise character**, not just colour.
  A clean iPhone 15 main camera, an ultrawide, and a video frame at ISO 3200
  do not share a grain structure, and the eye reads the difference as
  "assembled from different places" even when colour is unified.
- **Hardware encoders are poor at grain.** Grain is noise; it does not
  compress, and rate-controlled encoders smear it into blotches **[reported]**.
  Software x265 with `-tune grain` is the recommended path for grainy content
  **[reported]** — and x264's `grain` tune exists too (`--aq-strength 0.5
  --no-dct-decimate --deadzone-inter 6 --deadzone-intra 6 --deblock -2:-2
  --ipratio 1.1 --pbratio 1.1 --psy-qp 0.25 --qcomp 0.8` **[verified]** from
  x264's own `--fullhelp`).
- A **very light, uniform grain** (σ ≈ 1.5–3 levels) applied across the whole
  timeline is the cheapest way to make two sources look like one. It costs
  bitrate, so pair it with a CRF increase. Verify with a *negative control*:
  grain must not be strong enough to move the sharpness metric (§6.2).
- Counter-argument, and it is a real one: grain also hides the thing §6.2 shows
  your sharpness metric gets wrong, and it will inflate your existing
  `min_sharpness` scores. **If you add grain, re-calibrate the sharpness floor
  in the same change.**

### 9.4 x264 tuning for this content

From x264's own `--fullhelp` **[verified]** — every one of these is a
documented tune, not folklore:

| Tune | What it changes | Relevance |
|---|---|---|
| `film` | `--deblock -1:-1 --psy-rd <unset>:0.15` | Reduces deblocking. Reasonable default for photographic montage — the stills have no motion to hide. |
| `grain` | `--aq-strength 0.5 --no-dct-decimate --deadzone-inter 6 --deadzone-intra 6 --deblock -2:-2 --ipratio 1.1 --pbratio 1.1 --psy-qp 0.25 --qcomp 0.8` | For §9.3. |
| `animation` | `--bframes +2 --deblock 1:1 --psy-rd 0.4 --aq-strength 0.6 --ref` doubled | **Counter-intuitive but correct here:** this montage is mostly Ken Burns on *photographs*, which from the encoder's point of view is very much like animation — flat, clean, slowly-transforming, no sensor noise to hide. Worth a measured sweep. |
| `stillimage` | `--aq-strength 1.2 --deblock -3:-3 --psy-rd 2.0:0.7` | For individual stills if you ever encode them separately. |
| `fastdecode` | `--no-cabac --no-deblock --no-weightb --weightp 0` | Do **not** use. YouTube explicitly requires CABAC (§4.9). |

**Recommendation: sweep `film` and `animation` against your current default on
your real library and keep whichever wins on VMAF-NEG/SSIM.** Do not adopt
either on the strength of a table. Note that `psy-rd` is a rate-distortion
tradeoff knob: `film` makes x264 optimise for **bits rather than VMAF**, so it
can *lower* VMAF while producing a smaller file at the same visual quality. That
is exactly the inversion §4.4 demonstrated, and exactly why the sweep must
measure size *and* quality together.

| **1** | **Tag BT.709 on every output** and convert RGB→YUV with `scale=…:out_color_matrix=bt709` on the still path | **Very high** | **Trivial** (~10 lines, 3 call sites) | §2.
